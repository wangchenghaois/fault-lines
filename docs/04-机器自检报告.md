### 2.3.1 规则引擎单独扛得住几种真实粘贴（`scripts/probe-rule.mjs`）

公网版没有后端模型，评委真去点「导入回答」时，扛着的就是规则引擎。所以单独把几种典型的粘贴喂进去看它出什么：

| 输入 | 主张 | 争点 | 共识 | 说明 |
|---|---|---|---|---|
| 一条长回答（内部自带两种立场，3 句） | 3 | 1 | 2 | 能从一个回答里切出对立面 |
| 两条明确对立 | 2 | 1 | 0 | 各站一边，正确 |
| 三条其实同立场（都在说成本） | 3 | 1 | 2 | **会硬拆成 A2 / B1**——这是规则引擎的已知弱点：它按"是否同一话题"聚类，不判断立场是否真对立 |
| 一条极短（「不知道，看情况吧」） | 1 | 0 | 0 | 走空状态文案，不白屏 |

结论：正常长度的真实粘贴都能出图；同立场文本会被硬拆成伪争点，一条太短的会明确告诉你"没有形成可对抗的争点"。这两类都在界面上如实呈现，不假装有结果。规则引擎的定位就是"没有模型时的兜底，粗一些"，`docs/10` 与 README 都是这么写的。

**这条测试抓到一个真 bug，而且只有在这种「前端与服务端跨 realm」的场景里才会露头**：`detectDemo()` 原本用 `AbortSignal.timeout(4000)` 给 health 探测加超时，而在 jsdom / iframe / worker 里，`AbortSignal` 属于另一个 realm，把它交给 node 的 `fetch` 会直接抛 `TypeError`。异常被 `catch` 静默吞掉，症状是「health 明明 200、页面却认定没有演示模型」，然后 probe 掉回 `127.0.0.1:11434`。改成自建 `setTimeout` + `Promise.race`（并在 `finally` 里 `clearTimeout`）后消失。这在真实浏览器里不会触发，但同一个坑在 iframe 嵌套、Worker、单元测试里都会踩到，所以按缺陷修，不是给测试打补丁。

| 修复前 | 修复后 |
| --- | --- |
| `const signal = AbortSignal.timeout(4000)` → 传给 fetch | `Promise.race([fetch(url), new Promise((_, rej) => { timer = setTimeout(() => rej(new Error('health 探测超时')), 4000) })])` + `finally { clearTimeout(timer) }` |
| 页面显示「本地模型已连接」、实际打 11434 | 页面显示「演示服务器模型已就绪」、实际打 `/api/llm` |

复现命令：

```bash
DEBUG_LLM=1 npm run demo-test
```

### 2.5 静态托管版在真 Chrome 里打开（`build/pages-live-chrome.mp4`）

jsdom 不是浏览器。评委打开的是一个真 Chrome，所以「打包后的单文件在 Chrome 里到底能不能跑」必须单独验一次——如果那里有运行期错误，评委看到的就是一张白屏，而所有 jsdom 断言依然是绿的。

做法：用 `PORT=4210 node server.mjs` 起一个服务，`ROOT` 指向 `build/pages`（也就是要推到 GitHub Pages 的那个目录），`/api/health` 返回 `{"ok":true,"llm":{"enabled":false,"model":null}}`——**`enabled:false` 正是纯静态托管的真实条件**；然后用 EAC `record-browser` 在真 Chrome 里打开 `http://127.0.0.1:4210/?ds=gba`，依次点第 2 个争点、点「站左边」，再滚一次轮。录制 12.47 秒、1920×1080、30fps。

机器可测的证据（抽 t=1/3/5/7/9/11 六帧，Pillow 统计）：

| 帧 | 亮度均值 | 标准差 | 亮像素占比 | 主题色命中（蓝/橙/紫/绿） |
| --- | --- | --- | --- | --- |
| t=1 | 14.6 / 17.2 / 22.9 | ≈22 | 0.64% | 5 / 0 / 0 / 2 |
| t=3 | 同上 | ≈22 | 0.64% | 5 / 0 / 0 / 2 |
| t=5（点了价值断层 i2） | 15.2 / 17.7 / 23.3 | ≈23 | 0.71% | 1 / **4** / 0 / 2 |
| t=7 / t=9（点了站边） | 15.2 / 17.7 / 23.0 | ≈23 | 0.66% | 1 / 1 / 0 / 3 |
| t=11（滚动后） | 14.3 / 16.8 / 22.0 | ≈21 | 0.38% | 0 / 0 / 0 / **6** |

三点结论：

1. **不是白屏**。标准差 21–24，而空白页的标准差接近 0；亮像素 0.38%–0.71%，对应暗底上的文字与线条。
2. **界面真的渲染出来了，而且颜色是对的**。t=1 命中 5 个事实蓝（`#4da3ff`）像素——断层图在画事实断层；点开价值断层 i2 后 t=5 变成 4 个价值橙（`#ffa94d`）、蓝色降到 1——**颜色随所选争点的断层类型切换**，这与设计一致，不是随机噪声。
3. **点击会改状态，滚轮也会滚**。点开价值断层 i2 后画面主色从事实蓝变成价值橙（上表 t=5），这是点击驱动的重渲染。

滚动单独验了一次（`build/scrollcheck.mp4`，7.83 秒，1600×900 视口，两次 `deltaY=1500`）：把 t=1.5 与 t=7.2 两帧做逐像素差，均值 `[9.47, 9.87, 10.65]`；再拿 t=1.5 的第 200 行去 t=7.2 里找最匹配的行，最佳位移是 **150 px**（残差 5.4，明显小于不动时的差）。→ 页面确实滚了。位移只有 150 px，说明在 900 px 高的窗口里这个页面总高约 1050 px，**信念推演面板基本不用滚就能看到**。

顺带撤回一条我先前写错的推断：早先那版说「滚动后视口移到共识区」是**没有证据的猜测**，已删掉；现在这条是重新测的。

顶栏那句标语（`不告诉你答案，告诉你答案为什么分成两半`）是后加的，也验了一次：同一页面同一视口（1600×900）下，顶部 110 px 区域的亮像素数从 **2074** 增到 **2862**（+788），说明那行字确实画出来了，不是被 CSS 藏掉。

**这条证据不能替代人眼**：我看不到画面，无法确认字号是否清晰、有没有文字重叠、中文是否缺字。上面能证明的只有「不白屏、颜色对、交互改状态」这三件事。

产物：`build/pages-live-chrome.mp4`、`build/pages-live-chrome-frame.png`（t=7 的一帧）。

## 4. 补充素材：导入功能实况（`build/import-demo.mp4`，**已重录，这次拍到了结果**）

27.27s / 1920×1080 / 30fps。EAC `record-browser` 实地录制，剪辑为：粘贴 → 点「开始分析」（原速）→ **等待段 12× 加速并带角标说明** → 断层图真的渲染出来（原速，末段 13 秒）。

重录前的两版各有真问题，都记在这里：

| 版本 | 时长 | 问题 |
|---|---|---|
| 第 1 版（09:23 录制） | 49.47s | 分析需要 ~110 秒，录制只等到 42 秒就结束，**结果画面根本没进片** |
| 第 2 版（09:44 录制） | 91.33s | 记录到 0 个争点时页面弹出 `alert`，**阻塞渲染线程**，画面停在遮罩上不动 |
| 第 3 版（09:50 录制） | 91.47s | 逻辑跑通（日志 6 次 200、无错），但答案偏长仍超时；改用 3 段短文本后约 70 秒完成 |

这一轮改掉的真 bug：`runImport()` 里成功后仍用 `alert()` 提示"没识别出争点"。`alert` 会阻塞渲染线程，把刚算出来的画面挡在遮罩后面——演示与录屏里看起来就是彻底卡死。现在改成页内轻提示 `#notice`（`.notice.ok/.warn/.err` 三色，14 秒自动消失），空结果由 `ov-empty` 空状态承担。

这一版的时间线由 Ollama 服务端日志独立佐证（录制 09:50:13 开始）：

```
09:50:20 | 200 |  1.17s | POST /v1/chat/completions   ← 预热
09:50:31 | 200 | 10.51s | POST /v1/chat/completions   ← 第 1 条回答
09:50:45 | 200 | 14.02s | POST /v1/chat/completions   ← 第 2 条回答
09:50:51 | 200 |  6.29s | POST /v1/chat/completions   ← 第 3 条回答
09:51:20 | 200 | 29.16s | POST /v1/chat/completions   ← 争点归并
09:51:30 | 200 |  9.76s | POST /v1/chat/completions   ← 共识基线
```

六次请求全部 200，无一降级。成片里"结果出现"这件事由像素统计确认：t=74s（遮罩）均值 RGB `[7.9, 9.5, 13.6]` 标准差 `[3.3, 4.0, 4.7]` → t=80s（断层图）均值 `[13.0, 15.5, 20.9]` 标准差 `[16.1, 16.4, 16.3]`，画面从纯深色遮罩变成有结构、有彩色岩层的图。

这段素材的用途只有一：消解"是不是写死的示例数据集"这个质疑。它不是主片的一部分。**我仍然无法目视确认文字排版是否清晰**，但"分析真的在跑、结果真的出来了"这两点已由服务端日志与像素统计双重佐证。

## 5. 没有验证的部分（诚实边界）

- 多语言未实现。
