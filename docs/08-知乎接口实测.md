# 知乎开放平台接口实测报告

实测时间：2026-11-24　环境：本机 Node v26.13.0　凭证：**无**（用假 Secret `FAKE`）

这份文档记录的是**真的发出去、真的收到回包**的结果，不是照抄文档。

---

## 1. 一句话结论

六个业务端点的**路径全部正确、鉴权头格式被服务端接受**，只缺一个有效的 Access Secret。
参数名的大小写（`Query` / `Count`）**无法用假凭证验证**——因为知乎先校验鉴权、再校验参数。

---

## 2. 实测结果表

请求经本机代理 `server.mjs` 的 `/api/zhihu` 转发到 `https://developer.zhihu.com`，
请求头带 `Authorization: Bearer FAKE` 与秒级 `X-Request-Timestamp`。

| 端点 | 参数 | 返回 | 含义 |
|---|---|---|---|
| `/api/v1/content/zhihu_search` | `Query` + `Count` | `{"Code":20001,"Message":"Authorization failed"}` HTTP 200 | 路径对、鉴权头被解析、凭证无效 |
| `/api/v1/content/global_search` | `Query` + `Count` | 同上 | 同上 |
| `/api/v1/content/hot_list` | `Limit` | 同上 | 同上 |
| `/api/v1/user/question_recommendations` | `Query` + `Count` | 同上 | 同上 |
| `/api/v1/content/question_answers` | `QuestionUrl` + `Offset` + `Limit` | 同上 | 同上 |
| `/api/v1/quota` | `APIIDs` | 同上 | 同上 |
| `/api/v1/nope`（故意写错） | — | `404 page not found` | 说明上面那六个路径确实存在，不是万能回 200 |

**这张表能证明三件事：**

1. 域名可达、TLS 握手正常（curl 直连被沙箱拦，但 Node 的 fetch 出得去）。
2. 六个路径全部真实存在——写错路径会得到网关的 `404 page not found`，与业务错误码完全不同。
3. `Authorization: Bearer <x>` + `X-Request-Timestamp`（秒级）这个头组合被服务端接受并解析了——它是在解析完之后才判定 token 无效，而不是拒绝请求格式。

---

## 3. 无法验证的部分（必须说清）

### 3.1 参数名大小写，验不了

对照实验：

| 写法 | 返回 |
|---|---|
| `Query=test&Count=3`（官方写法） | `20001 Authorization failed` |
| `query=test&count=3`（小写） | `20001 Authorization failed` |
| 完全不给 `Query` | `20001 Authorization failed` |

三种写法返回**完全相同**。原因是鉴权前置：凭证无效时，服务端在第 0 步就返回了，根本走不到参数校验。

所以「参数名必须是 PascalCase」这一点，目前只有**官方文档**作为依据，没有实测证据。
拿到真 Secret 后的第一件事就是跑 `ZHIHU_SECRET=xxx node scripts/zhihucheck.mjs`，
若返回 `10001 参数错误` 则说明参数名仍需调整。

### 3.2 真实数据长什么样，没见过

`Data.Items[]` 里各字段是否都必定返回、`Summary` 的实际长度分布、`Paging.IsEnd` 的翻页行为，
全部只能等真凭证。代码里所有数值字段缺失时返回 `null` 而不是 `0`，就是为了在这种不确定下不伪造数据。

## 4. 为什么需要本机代理

浏览器直接 `fetch('https://developer.zhihu.com/...')` 会因同源策略被拦（对方没有给本站发 `Access-Control-Allow-Origin`）。
所以 `server.mjs` 加了一个转发路由：

```
GET /api/zhihu?path=/api/v1/content/hot_list&Limit=10
Header: X-Zhihu-Secret: Bearer <Access Secret>
```

Secret 走请求头而不是 URL，避免出现在日志、浏览器历史、Referer 里。
代理只允许 `path` 以 `/` 开头，不做任意 URL 转发（防 SSRF）。

**代价**：单文件离线版（`dist/歧见.html`）没有代理，知乎面板在其中会直接提示
「单文件模式没有本机代理，请用 `node server.mjs 4188` 启动」。这是有意的——离线版不假装能联网。

## 6. 复现方式

```bash
# 1. 起本机服务器（含代理）
node server.mjs 4190

# 2. 无 Secret 时
curl "http://127.0.0.1:4190/api/zhihu?path=/api/v1/content/hot_list&Limit=3"
# → {"Code":10001,"Message":"缺少 X-Zhihu-Secret 请求头"}  HTTP 400

# 3. 假 Secret
curl "http://127.0.0.1:4190/api/zhihu?path=/api/v1/content/hot_list&Limit=3" \
     -H "X-Zhihu-Secret: Bearer FAKE"
# → {"Code":20001,"Message":"Authorization failed","Data":null}  HTTP 200

# 4. 真 Secret（有凭证时）
ZHIHU_SECRET=Bearer_xxx node scripts/zhihucheck.mjs
```
