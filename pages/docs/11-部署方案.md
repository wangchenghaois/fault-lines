# 部署方案（公网 Demo）

守则要求「评委可直接操作并完整体验核心功能」，所以必须有一个**公网链接**。这份文件说明这个项目要部署成什么样、三条路线怎么走、以及哪一步需要你本人操作。

---

## 一、这个项目属于哪种形态

**前端 + Node 后端，不写数据库。**

- 前端：`index.html` + `src/`（原生 ES 模块，无构建步骤，浏览器直接加载）
- 后端：`server.mjs`（零依赖，三个职责：静态文件、知乎代理、模型代理）
- 数据：不落库。用户粘贴的回答只在浏览器内存里；没有任何用户数据被保存

按主办方给的口径，这种形态**正好符合「知乎 AiWorks」的部署条件**（前端 + Node 后端、不含数据库写入），也适合 CloudBase 云托管或任意云主机。

---

## 二、为什么需要一个后端（不能纯静态托管）

三种能力在纯静态站点上不存在：

| 能力 | 为什么浏览器做不到 |
|---|---|
| 知乎接口拉取 | `developer.zhihu.com` 没有对本项目开放 CORS，浏览器直连会被同源策略拦 |
| 服务端模型 | 静态站没有地方放 API Key；放进前端等于公开泄露 |
| 演示额度控制 | 需要一个能计数的进程 |

所以 GitHub Pages 那种纯静态托管**只能跑内置示例 + 规则引擎**。能用，但会丢掉「真实知乎内容」和「真模型分析」这两块，而这两块恰好是赛题最看重的部分。

---

## 三、三条路线

### 路线 A：知乎 AiWorks（推荐，最省事）

主办方提供的部署能力，条件正好匹配本项目。大致流程：

1. 在黑客松页面拿到 AiWorks 的入口/凭证
2. 把整个项目目录交给它（或让它接进你的仓库）
3. 它会跑 `npm start`（本项目 `package.json` 已写好：`node server.mjs 4188`）
4. 平台会注入 `PORT` 环境变量 —— `server.mjs` 已经适配：**读到 `PORT` 就监听 `0.0.0.0`**，否则只监听本机

需要你确认的两件事：AiWorks 的入口地址、以及它是否允许配置自定义环境变量（下面第二节的那些）。

### 路线 B：CloudBase 云托管

1. 安装 CLI：`npm i -g @cloudbase/cli`，然后 `tcb login`
2. 项目根目录已经有 `package.json` 与 `server.mjs`，CloudBase 云托管支持「本地代码 → 直接上传」
3. 在控制台把**服务端口**设成 `4188`（或设 `PORT` 环境变量，代码优先用 `PORT`）
4. 环境变量按第四节填
5. 部署完成后拿到 `https://xxx.service.tcloudbase.com` 这样的域名

注意：云托管默认给的是 HTTPS 域名，本项目所有请求都是同源相对路径（`/api/health`、`/api/zhihu`），不需要改任何前端代码。

### 路线 C：任意云主机（最可控）

```bash
# 服务器上
git clone <你的仓库> qijian && cd qijian
node server.mjs 4188          # 前台跑一下，确认能起来

# 常驻
nohup node server.mjs 4188 > app.log 2>&1 &

# 反代（nginx）
location / {
  proxy_pass http://127.0.0.1:4188;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-For $remote_addr;
}
```

`server.mjs` 会读 `X-Forwarded-For` 做限流，所以反代要带上这个头。

## 四、环境变量

| 变量 | 作用 | 不填会怎样 |
|---|---|---|
| `PORT` | 监听端口（平台通常自动注入） | 用 `4188`（`npm start`）或命令行参数 |
| `HOST` | 监听地址 | 有 `PORT` 时用 `0.0.0.0`，否则 `127.0.0.1` |
| `LLM_BASE_URL` | 模型端点，如 `https://api.deepseek.com/v1` | 前端回退到本机 Ollama，再回退到规则引擎 |
| `LLM_API_KEY` | 服务端 Key（**只在服务端，不进前端**） | 同上 |
| `LLM_MODEL` | 模型名，如 `deepseek-chat` | 用请求里带的模型名 |
| `LLM_LIMIT` | 每 IP 每小时调用上限，默认 40 | 40 |

**只有 `LLM_BASE_URL` 和 `LLM_API_KEY` 同时存在，`/api/health` 才会报 `llm.enabled: true`**，前端才会自动把「AI 分析」指向服务端。这也是这套部署的诚实之处：没配 Key 就不会假装有 AI。

## 五、部署后必须自查的 6 项

```bash
BASE=https://你的域名

curl -s $BASE/api/health          # → {"ok":true,"llm":{"enabled":true,...},"zhihuProxy":true}
curl -s $BASE/api/llm/models      # → 有模型列表说明探活链路通
curl -s -o /dev/null -w "%{http_code}\n" $BASE/          # → 200
curl -s -o /dev/null -w "%{http_code}\n" $BASE/src/app.js # → 200（模块能加载）
curl -s "$BASE/api/zhihu?path=/api/v1/content/hot_list"   # → 400 且 Code=10001（缺 secret，符合预期）
```

再加一条**必须用浏览器做的**：打开 `$BASE`，确认断层图渲染出来、点争点能切换、站边后推演能展开。这一步我没法替你做——我用的模型没有图像输入能力，看不了截图。

## 六、这条链路的自动化测试

`tools/servertest.mjs`（**14 条断言**，已接进 `npm test`）在同一个进程里起一个假上游 + 真 `server.mjs`，实测：

- `/api/health` 正确报告 `llm.enabled`
- `/api/llm/models` 返回模型列表（前端 `probe()` 靠它判断可用）
- `/api/llm/chat/completions` 真的转发，且**上游确实收到 `Authorization: Bearer`**
- 服务端**默认注入 `reasoning_effort: 'none'`**（不注入的话 reasoning 模型会把 token 全烧在思维链上，正文返回空——这个坑我们踩过，见 `docs/04`）
- 客户端自己指定 `reasoning_effort` 时不被覆盖
- 超过每小时额度返回 **429**，且提示的是额度而不是崩溃
- 知乎代理缺 secret 返回 **400 + Code 10001**，且**拒绝以 `http://` 开头的 path**（防 SSRF）
- 首页 200 且内容正确

这套测试不能 spawn 子进程（本机沙箱会 `EPERM`），所以是在同一个进程里 `import('server.mjs')`——它一被 import 就 listen，等价于真服务。

### 更完整的一条：`npm run demo-test`（8 条断言，约 80 秒，需要本机 Ollama 冒充云厂商）

`servertest` 只测到服务端。但评委走的是**整条链**：打开公网页面 → 前端自己发现「这个部署有服务端模型」→ 不再去找 `127.0.0.1:11434` → 分析请求打到同源 `/api/llm` → 服务端带 Key 转发 → 结果回到页面画成断层图。

`scripts/demotest.mjs` 用 `LLM_BASE_URL=http://127.0.0.1:11434/v1` 让本机 Ollama 冒充云厂商，再用 jsdom 以 `http://127.0.0.1:PORT/` 打开打包后的单文件（不是 `file://`），完整跑一遍。实测 **8 通过 / 0 失败、80.5 秒、`engine=llm`**，服务端日志显示六次转发全部 200。

```bash
npm run demo-test            # 想看得更细：DEBUG_LLM=1 npm run demo-test
```

这条测试抓到一个跨 realm 的真 bug（`AbortSignal.timeout` 交给别的 realm 的 `fetch` 会抛 `TypeError`，被 catch 吞掉后页面误判「没有演示模型」），成因和修复见 `docs/04` 第 2.4 节。
